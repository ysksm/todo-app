1. 現状の制約

一般論としてのリアルタイム同期ではなく、いまのコードがすでに決めてしまっている条件から入る。 とくに 1 つ目は、方式選択そのものを左右する。

まとめると 「通知の起点をサーバープロセスの中に置けない」のが、この設計の いちばんの制約。どの方式を選ぶにせよ、cli の書き込みを拾う経路が別に要る。

2. 方式の比較

「サーバーがフロントへ知らせる」経路の候補。上から下へ、常時接続の度合いと実装量が増えていく。

A. 定期ポーリング（＋ ETag）

フロントが数秒おきに GET /api/todos を叩く。If-None-Match を付ければ、 変更が無いときは 304 が返るだけで転送量はほぼゼロになる。

最短で動くが、遅延と無駄打ちがトレードオフとして残り続ける。5 秒間隔なら 1 タブあたり 1 日 17,000 リクエスト。暫定策として、また常時接続が張れない環境のフォールバックとしては有効。

B. ロングポーリング

GET /api/todos/changes?since=rev を、変更が起きるかタイムアウトするまで サーバー側で保留する。返ったらフロントが即座に張り直す。

得られる体験は SSE とほぼ同じなのに、再接続・タイムアウト・重複検知を自前で書くことになる。 SSE が使える以上、あえて選ぶ理由が薄い。

C. Server-Sent Events (SSE)推奨

1 本の HTTP レスポンスを開いたままにして、サーバーからテキストのイベントを流す。 ブラウザ側は EventSource だけ。切断時の再接続と Last-Event-ID による 再開が仕様に組み込まれている。

サーバー→クライアントの一方向で足りる、いまの要件にちょうど合う。 FastAPI の StreamingResponse で書けて追加ライブラリは不要、Vite の /api プロキシもそのまま通る。

ただし素の SSE は「サーバープロセス内で起きた変更」しか知らない。cli の変更を拾うには、 3 章の版番号ファイル監視と組み合わせる必要がある。

D. WebSocket

全二重の常時接続。クライアントからサーバーへも随時送れる。

いま必要なのは通知の一方向だけで、書き込みは既存の REST が担っている。 共同編集のカーソル共有・入力中表示・楽観ロックの奪い合いといった双方向の要求が出てきたら、 その時点で乗り換える。先取りするには維持コストが高い。

E. 外部ブローカー（Redis Pub/Sub 等）＋ SSE

変更をブローカーへ publish し、各サーバープロセスが購読してぶら下がるクライアントへ流す。

複数ホストへ広げる段になったら必要になる。いまは JSONL ファイル 1 本を共有する単一ホスト構成で、 ファイル自体がすでにブローカーの役割を果たしている。C の配信口を保ったまま、 後から内側だけ差し替えられる。

方式 追従の速さ 実装量 cli の変更 複数ワーカー 追加依存
A ポーリング 間隔しだい（3〜10 秒） 小 拾える 問題なし なし
B ロングポーリング 1 秒未満 中 版番号の監視が要る 版番号の監視で可 なし
C SSE 0.5 秒未満 中 版番号の監視が要る 版番号の監視で可 なし

3. 推奨構成

方式は C（SSE）。要は「誰が書いたか」をサーバーが気にしなくて済む形にする。 3 つのインターフェースはすべて TodoRepository の _locked() を通ってから 書き込むので、その中で版番号ファイルを 1 つ進める。サーバーはそのファイルだけを見張る。

この形を選ぶ理由

  • cli も自動で拾える。通知の起点をプロセス内のフックではなくファイルに置いたので、 書き手が誰であっても同じ経路に乗る。
  • 複数ワーカーでも壊れない。各ワーカーが同じファイルを見張るだけなので、 --workers 4 にしても Redis を足さずに動く。
  • 版番号が他にも効く。ETag・楽観ロック・再接続時の取りこぼし判定が、 同じ 1 つの数から導ける。
  • 捨てやすい。監視タスクとエンドポイントを外せば元の挙動に戻る。 core への変更は rev の加算だけ。

遅延について

0.3 秒間隔の stat() は、体感上は即時で、負荷としては無視できる。 それでも足りなければ、同一プロセス内の書き込みだけブローカーへ即時 publish する早出しを 併用できる。rev で重複排除するので、監視タスクと二重に流れても画面には 1 回しか届かない。

4. 段階導入

各段階だけで完結して価値が出る。途中で止めても壊れない順に並べた。

PHASE 0版番号を core に入れる

data/todos.rev を _locked() の中で更新し、 GET /api/todos のレスポンスに ETag と X-Todo-Rev を付ける。

  • この時点で案 A（条件付き GET のポーリング）が数行で実現でき、SSE を待たずに複数タブ同期が成立する
  • SSE も含め、以降すべての土台になる

PHASE 1SSE で「変わった」だけ流す

監視タスク・ブローカー・GET /api/todos/events を足す。 フロントは変更を受けたら既存の reload() を呼ぶだけ。

  • 差分計算もマージも書かないので、状態がずれる余地がない
  • フロントの変更は購読フック 1 つと、それを呼ぶ 1 行

PHASE 2イベントに中身を持たせる

{ rev, kind, ids } を載せ、Last-Event-ID での再開に対応する。 編集中のノードを再取得で潰さないよう、部分更新へ寄せる。

  • マインドマップで編集中に他所の変更が来ても、フォーカスと入力途中が飛ばない
  • 取りこぼしを検知したら全件再取得へフォールバック

PHASE 3必要になったら内側を差し替える

複数ホストへ広げるなら案 E、双方向が要るなら案 D。フロントの購読ポートを変えずに済むよう、 Phase 1 の時点で境界を切っておく。

core/change_log.py（新規）

版番号の読み書き。core に置くので cli からも同じものが使われる。

from __future__ import annotations

import json
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class Change:
    rev: int
    kind: str          # created / updated / moved / deleted
    ids: list[int]


class ChangeLog:
    """データファイルの隣に置く版番号。

    webapi / mcp / cli のどれが書いても TodoRepository._locked() の中を通るので、
    ここが「変更が起きた」ことを知る唯一の場所になる。
    """

    def __init__(self, data_file: Path) -> None:
        self.path = data_file.with_name(f"{data_file.name}.rev")

    def read(self) -> Change | None:
        if not self.path.exists():
            return None
        try:
            payload = json.loads(self.path.read_text(encoding="utf-8"))
        except (json.JSONDecodeError, OSError):
            return None
        return Change(**payload)

    def bump(self, kind: str, ids: list[int]) -> Change:
        """_locked() の中から呼ぶこと。読んで書くまでが排他される必要がある。"""
        current = self.read()
        change = Change(rev=(current.rev + 1) if current else 1, kind=kind, ids=ids)
        temporary = self.path.with_suffix(".rev.tmp")
        temporary.write_text(json.dumps(asdict(change)), encoding="utf-8")
        temporary.replace(self.path)   # 読み手が半端な内容を見ないように置換で書く
        return change

interfaces/webapi/change_stream.py（新規）

監視タスクとブローカー。core は asyncio を知らないままにする。

import asyncio

from core.change_log import Change, ChangeLog


class ChangeBroker:
    """購読者ごとに 1 本のキューを持つ。遅い購読者が配信全体を止めないようにする。"""

    def __init__(self) -> None:
        self._queues: set[asyncio.Queue[Change]] = set()

    def subscribe(self) -> asyncio.Queue[Change]:
        queue: asyncio.Queue[Change] = asyncio.Queue(maxsize=32)
        self._queues.add(queue)
        return queue

    def unsubscribe(self, queue: asyncio.Queue[Change]) -> None:
        self._queues.discard(queue)

    def publish(self, change: Change) -> None:
        for queue in self._queues:
            try:
                queue.put_nowait(change)
            except asyncio.QueueFull:
                pass   # 溢れた分は捨てる。rev のずれでクライアントが全件取り直す


async def watch_changes(
    change_log: ChangeLog, broker: ChangeBroker, interval: float = 0.3
) -> None:
    """rev ファイルを見張る。cli が別プロセスで書いた変更もここで拾える。"""
    last_rev = (change_log.read() or Change(rev=0, kind="", ids=[])).rev
    while True:
        await asyncio.sleep(interval)
        change = await asyncio.to_thread(change_log.read)
        if change is not None and change.rev != last_rev:
            last_rev = change.rev
            broker.publish(change)

SSE エンドポイントと lifespan

15 秒ごとのコメント行が、プロキシとブラウザに接続の生存を伝える。

# interfaces/webapi/todos.py
@router.get("/api/todos/events")
async def stream_todo_changes(request: Request) -> StreamingResponse:
    broker: ChangeBroker = request.app.state.change_broker
    queue = broker.subscribe()

    async def events():
        yield "retry: 3000\n\n"          # 切断時の再接続間隔をブラウザへ指示する
        try:
            while True:
                try:
                    change = await asyncio.wait_for(queue.get(), timeout=15)
                except TimeoutError:
                    yield ": keepalive\n\n"
                    continue
                data = json.dumps(
                    {"rev": change.rev, "kind": change.kind, "ids": change.ids}
                )
                yield f"id: {change.rev}\nevent: todos-changed\ndata: {data}\n\n"
        finally:
            broker.unsubscribe(queue)    # 切断時に必ず外す

    return StreamingResponse(
        events(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",   # nginx を挟んだときに溜め込ませない
        },
    )

フロントエンド

domain がインターフェースを決め、infrastructure が EventSource を持つ。テストでは差し替える。

// domain/repositories/todo-change-stream.ts
export interface TodoChange {
  rev: number
  kind: 'created' | 'updated' | 'moved' | 'deleted'
  ids: readonly number[]
}

export interface TodoChangeStream {
  /** 購読を開始し、解除する関数を返す。 */
  subscribe(handlers: {
    onChange(change: TodoChange): void
    /** 再接続した。取りこぼしがあり得るので呼び手は全件取り直す。 */
    onReconnect(): void
  }): () => void
}

// infrastructure/streams/sse-todo-change-stream.ts
export class SseTodoChangeStream implements TodoChangeStream {
  subscribe(handlers) {
    const source = new EventSource(`${apiBaseUrl}/api/todos/events`)
    let wasOpen = false

    source.addEventListener('open', () => {
      if (wasOpen) handlers.onReconnect()   // 初回接続では呼ばない
      wasOpen = true
    })
    source.addEventListener('todos-changed', (event) => {
      handlers.onChange(JSON.parse((event as MessageEvent).data))
    })
    // エラー時の再接続は EventSource 自身がやる。閉じない。

    return () => source.close()
  }
}

// presentation/hooks/use-todo-changes.ts
export function useTodoChanges(dependencies: TodoDependencies, reload: () => Promise<void>) {
  const appliedRev = useRef(0)

  useEffect(
    () =>
      dependencies.todoChangeStream.subscribe({
        onChange(change) {
          // 自分の操作で起きた変更は反映済みなので、rev を見て取り直しを省く
          if (change.rev <= appliedRev.current) return
          appliedRev.current = change.rev
          void reload()
        },
        onReconnect: () => void reload(),
      }),
    [dependencies, reload],
  )
}

6. 気をつける点

項目内容
自分の操作のエコー フロント自身の保存も rev を進めるため、直後に「変更あり」が返ってくる。 GET /api/todos のレスポンスヘッダーで受け取った rev を覚えておき、 それ以下のイベントは捨てる。
再接続後は取り直す 切れている間の変更は届かない。open の 2 回目以降は無条件に全件再取得する。 Phase 2 で Last-Event-ID の差分再送を足しても、この保険は残す。
同時接続数 HTTP/1.1 では 1 オリジンあたり 6 本。SSE が 1 本を占有するので、 同じアプリを 6 タブ以上開くと API が詰まる。本番で HTTP/2 を使うなら解消する。
Vite の dev プロキシ /api の既存プロキシ設定のまま SSE も通り、バッファリングもされない。 追加設定は要らない。
編集中の巻き戻し Phase 1 の全件再取得は、編集中のタイトルやフォーカスを上書きしうる。 editingTodoId がある間は反映を保留するか、Phase 2 の部分更新へ進む。
テスト jsdom に EventSource は無い。TodoChangeStream をポートにしてあるので、 フロントのテストでは手で叩けるフェイクを注入する。バックエンドは ChangeLog 単体と、 監視タスクが rev の変化を publish するかを見れば足りる。
rev ファイルの扱い data/ 配下なので .gitignore の対象に含める。消えても壊れず、 次の書き込みで 1 から振り直される。クライアント側は rev の減少を検知したら取り直す。

認証。Web UI 自体に認証が無い現状に合わせ、SSE も /api 配下の 無認証として置く。HOST=0.0.0.0 で公開するなら、この経路も含めて 信頼できるネットワーク限定という前提は変わらない。

7. 決めること

方式は SSE、変更の起点は版番号ファイル。Phase 0 と Phase 1 で実用になり、追加依存はゼロ、 core への変更は rev の加算だけで済む。着手前に決めたいのは次の 3 点。

  1. どこまでやるか。Phase 0 だけ（ポーリングで十分）か、Phase 1 まで進めるか。
  2. 編集中の扱い。他所の変更を即座に反映するか、編集が終わるまで保留して 知らせるだけにするか。
  3. rev の置き場所。別ファイル（この案）か、Todo 自体に updated_at を持たせるか。後者は JSONL の形式変更を伴う。
