TODO の親子関係とマインドマップビュー

TODO に親子関係を持たせ、左から右へ枝が伸びるトーナメント表のようなマインドマップとして 表示・操作できるようにする。キーボードだけでタスクの追加・移動・命名ができることを目標にする。

1. 要求

現状の TODO はフラットな 1 階層のリストしか持たない。思考を整理しながらタスクを分解できるよう、 タスクに親子関係を持たせ、それをマインドマップとして扱えるようにする。

やること

  • BE TODO が親を 0 or 1 個持てるようにする（子は複数）。
  • BE 同じ親の中での並び順を保持する。マインドマップの上下の並びを安定させるため。
  • BE 親子関係を後から変更する API を用意し、循環参照を防ぐ。
  • FE 既存の一覧画面は残したまま、マインドマップ表示を追加する。
  • FE 左から右へ子が伸びるトーナメント表レイアウトにする。
  • FE マインドマップ上のタスク操作をキーボードで完結させる。

やらないこと

  • 除外 複数ユーザー / 認証 / 同時編集
  • 除外 マウスドラッグでのノード移動（キーボード操作を先に完成させる）
  • 除外 折りたたみ状態のサーバー永続化（クライアント内の一時状態にとどめる）
  • 除外 キャンバスのパン・ズーム
  • 除外 期限・タグ・優先度などの新しい属性

用語

  • ノード — マインドマップ上に描画された 1 つの TODO。
  • ルート — 親を持たない TODO。複数存在してよい（森構造）。
  • 兄弟 — 同じ親を持つ TODO の集合。並び順を持つ。
  • 子孫 — ある TODO から親子リンクを辿って到達できるすべての TODO。

2. キー操作

左→右レイアウトに合わせ、矢印キーの向きと画面上の移動方向を一致させる。 ← → が階層の上下、↑ ↓ が兄弟間の移動。

キー通常モード編集モード
→ 折りたたみ中なら展開のみ。展開済みなら先頭の子へ。子が無ければ何もしない input に委譲（カーソル移動）
←親へ。ルートなら何もしないinput に委譲
↑ひとつ上の兄弟へ。先頭なら何もしない—
↓ひとつ下の兄弟へ。末尾なら何もしない—
F2タイトル編集開始（既存タイトルを全選択）—
Enter同じ親に兄弟を新規追加し、そのノードを編集モードへ保存して編集終了
Tab子を新規追加し、編集モードへ（preventDefault 必須）保存して編集終了
Delete BS削除。子孫があるときは確認ダイアログ—
Spacecompleted をトグル—
Esc—変更を破棄して編集終了
Home End兄弟の先頭 / 末尾へ—

新規作成は空タイトルでは API を叩けない（normalizeTodoDraft が弾く）ため、 クライアント側に仮ノードを置いてから編集させ、確定時に POST する。 空のまま Esc や blur した場合は仮ノードを破棄する。

  • 移動キーは常に preventDefault()（ページスクロール抑止）。
  • 端に到達した場合はフォーカスを動かさない。ラップアラウンドしない。
  • 削除後のフォーカスは「直前の兄弟 → 無ければ親」の順で決める。

3. データモデル

バックエンド models/todo.py

class TodoBase(BaseModel):
    title: str
    description: str = ""
    completed: bool = False


class TodoCreate(TodoBase):
    parent_id: int | None = None   # 追加先の親。None ならルート


class TodoUpdate(TodoBase):
    """PUT /api/todos/{id} 用。親子関係は変更しない。"""


class TodoMove(BaseModel):
    parent_id: int | None = None   # 移動先の親
    position: int | None = None    # 兄弟内の挿入位置。None なら末尾


class Todo(TodoBase):
    id: int
    parent_id: int | None = None
    position: int = 0              # 同じ親を持つ兄弟の中での 0 始まりの並び順

設計判断: 親子関係の変更を PUT に混ぜず、専用の PATCH .../move に分離する。既存フロントの PUT （title / description / completed のみ送信）が親子関係を壊さないようにするため。

永続化 repositories/todo_repository.py

JSONL の全読み・全書き戻しという現行方式は維持する。読み書きの両方で _normalize() を通す。

  1. 存在しない parent_id を指す TODO は孤児とみなし parent_id = None に倒す。
  2. 親ごとにグループ化し、(position, ファイル出現順) でソートして position を 0..n-1 に振り直す。
  3. 万一循環が残っていた場合、循環に含まれるノードをルートへ戻す（データ破損時のフェイルセーフ）。

既存データには parent_id / position が無いが、Pydantic のデフォルト値で 読み込めるためマイグレーションスクリプトは不要。全件がルートとして扱われる。

メソッド内容
create(todo_create)parent_id を検証し、その親の末尾 position に追加
update(id, todo_update)title / description / completed のみ更新。parent_id / position は保持
move(id, move)親と位置を変更。循環チェックあり
delete(id)子孫ごとカスケード削除。削除した id のリストを返す
descendant_ids(id)子孫 id の集合。循環チェックと削除で共用

move の手順

  1. 対象が存在しなければ None を返す（→ 404）。
  2. 移動先の親が自分自身、または自分の子孫なら CyclicMoveError（→ 400）。
  3. 移動先の親が None 以外で存在しなければ ParentNotFoundError（→ 400）。
  4. 旧兄弟から抜き、新兄弟の指定位置に挿入。position=None は末尾、範囲外は clamp。
  5. _normalize() して保存。

フロントエンド domain/entities/todo.ts

export interface Todo {
  readonly id: number
  readonly title: string
  readonly description: string
  readonly completed: boolean
  readonly parentId: number | null
  readonly position: number
}

export interface TodoDraft {
  readonly title: string
  readonly description: string
  readonly completed: boolean
  readonly parentId: number | null   // 追加
}

export interface TodoMove {
  readonly id: number
  readonly parentId: number | null
  readonly position: number | null
}

TodoUpdate（id + title / description / completed）は現状のまま。 normalizeTodoDraft は parentId をそのまま透過させる。

4. API

フラットな配列を返す方式を維持し、木構造はフロント側で組み立てる。 サーバーとクライアントで木の構築ロジックを二重に持たないため。

メソッドパスリクエストレスポンス
GET/api/todos—Todo[]（深さ優先・position 昇順）
GET/api/todos/{id}—Todo
POST/api/todosTodoCreateTodo
PUT/api/todos/{id}TodoUpdateTodo
PATCH/api/todos/{id}/moveTodoMoveTodo
DELETE/api/todos/{id}—204（子孫もカスケード削除）
状況ステータスdetail
対象 TODO が無い404Todo not found
指定した親が存在しない400Parent todo not found
自分自身 or 子孫を親に指定400Cannot move a todo under its own descendant

DELETE が子孫までカスケードする点は破壊的なので、web-backend/README.md に明記する。

  • ルートは複数存在しうる。ルート同士も position 順の「兄弟」として扱い、↑ ↓ で行き来できる。

状態管理 presentation/store/todo-slice.ts

viewMode: 'list' | 'mindmap'
focusedTodoId: number | null    // マインドマップ上のカーソル位置
editingTodoId: number | null    // F2 でインライン編集中のノード
collapsedIds: number[]          // 折りたたみ（クライアント内のみ）

追加アクション: viewModeChanged / focusMoved / editingStarted / editingStopped / collapseToggled。 requestSucceeded は既存の selectedTodoId と同様に、消えた TODO を指す id を null に戻し、collapsedIds からも取り除く。

フォーカス方式

キーイベントはキャンバスのコンテナ（tabIndex={0}）で受け、focusedTodoId を動かす roving focus 方式。個々のノードに DOM フォーカスを配らないことで、 数百ノードでもイベントハンドラが 1 つで済む。

アクセシビリティ

  • キャンバス: role="tree", aria-activedescendant
  • ノード: role="treeitem", aria-level, aria-expanded（子がある場合のみ）, aria-selected
  • キー割り当ての凡例をビュー内に表示する（? でトグル）。

ビュー切り替え

ヘッダーに「リスト / マインドマップ」のタブを置き、viewMode で切り替える。 どちらのビューも同じ useTodos のデータを参照するため、片方の変更が即もう片方に反映される。 既存のリストビューは、親子関係をインデントで示す最小変更にとどめる。

6. レイアウト

左→右のトーナメント表。tidy tree の簡易版（Reingold–Tilford の 1 次元版）。

NODE_WIDTH = 220, NODE_HEIGHT = 44
H_GAP = 64   // 列間の水平距離
V_GAP = 12   // 葉の垂直間隔
  • x = depth * (NODE_WIDTH + H_GAP)
  • y は深さ優先で走査し、葉に出会うたびに次のスロットを消費する（nextY += NODE_HEIGHT + V_GAP）。
  • 子を持つノードの y は先頭の子と末尾の子の中点。これでトーナメント表状に揃う。
  • 出力は Map<todoId, {x, y}> とキャンバス全体の {width, height}。
  • 折りたたまれたノードの子はレイアウト計算から除外する（collapsedIds: Set<number> を入力に取る）。

ノード間の接続線は SVG の <path> で、親の右端 → 子の左端を結ぶ 3 次ベジエ:

M px,py C px+H_GAP/2,py  cx-H_GAP/2,cy  cx,cy
